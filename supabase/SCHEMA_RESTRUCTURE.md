## Part 10 — Project Charter progress auto-computed from Milestones (migration 0022)

Requested: add subtasks under a Project Charter, with the charter's overall % completion auto-computed from them. Scoped with you up front: Milestones (already an existing entity under each Project Charter) are the "subtasks" — no new entity needed. The Project Charter is the "main task." Formula confirmed with you: **count-based**, not a progress-percent average — `overall_progress_percent = (milestones with Status = Completed) ÷ (total milestones for that project) × 100`. A milestone's own Progress % field and the existing (previously unused) Weight field don't factor into this — flagging in case you later want a weighted version instead.

- **`supabase/migrations/0022_project_progress_auto_compute.sql`** (applied live) — added `project_charters.overall_progress_percent numeric` (check 0–100 or null). This can't be a Postgres generated column (those may only reference columns on the same row, not aggregate across a child table), so it's maintained by a trigger on `milestones` instead: `recompute_project_progress(project_id)` counts total vs. Completed milestones and writes the result back to the parent project; `trg_recompute_project_progress()` fires it after every insert/update/delete on `milestones` (including recomputing the *old* project if a milestone's `project_id` is ever changed). Both functions are `security definer` so the write to `project_charters` isn't blocked by that table's own owner-scoped RLS. A one-time backfill loop ran the same function over your 3 existing projects immediately, rather than waiting for the next milestone edit.
- **Found and fixed while wiring this up:** `project_charters` and `milestones` in `src/lib/crud/configs.ts` were still on a pre-migration hardcoded `status` text `select` field from before the schema's lookup_options reconstruction (Part 0) — but the live columns are `status_id` (referencing the `project_status` / `milestone_status` lookup lists, which already existed live with no frontend wired to them). This meant **creating or editing a Project Charter's or Milestone's status has been silently broken** this whole time — any save would have failed with a "column does not exist" error. Fixed both to proper `lookupRef()` reference fields, the same pattern used everywhere else in this schema. This was a prerequisite for the new feature too: the trigger needs a real `status_id` to know which milestones are Completed.
- **Also found and fixed, same root cause:** `src/app/(app)/dashboard/page.tsx` selected the same now-nonexistent plain `status` column from `asset_requests` and `project_charters`, and `status`/`severity` from `risk_issue_log` — three of the six dashboard queries were silently failing (the error is swallowed by `.data ?? []`), so **Asset Requests by Status, Active Projects, Projects by Status, and Risks by Severity have all been showing 0/empty regardless of actual data.** Fixed all three queries to embed the referenced lookup row (`status:lookup_options!status_id(value)`, same technique already used in `src/app/(app)/schedule/page.tsx`) instead of selecting the dropped column directly.
- **Not fixed, flagged only:** the Risk & Issue Log entity itself (`src/lib/crud/configs.ts`, key `risks`) has the exact same broken pattern — `type`, `category`, `probability`, `impact`, `severity`, and `status` are all still hardcoded `select` fields, but the live table only has `type_id`/`category_id`/`probability_id`/`impact_id`/`severity_id`/`status_id`. ## Part 7 — Bill of Materials module (migration 0019)

Requested: a way to plan the actual parts/materials a project needs before procurement starts, and to see how that connects to the existing Capex → Procurement flow. Scoped with you up front on three questions before writing any schema: **(1)** a BOM belongs to one Asset Request (not a Project Charter, not a standalone template); **(2)** a finalized BOM line auto-creates its Procurement Item with one click, rather than staying a disconnected reference document; **(3)** a BOM is a flat parts list, not a nested/multi-level manufacturing-style BOM. Everything below follows from those three answers.

### Schema (`supabase/migrations/0019_bill_of_materials.sql`, applied live)

- **`bill_of_materials`** — the header. One row per Asset Request at most (`asset_request_id uuid not null unique references asset_requests`, `on delete cascade` — an owned child, same as every other `*_request_id` child table here). `status_id` references a new `bom_status` lookup_options list (Draft, Submitted, Approved, Converted, Cancelled), following the exact same generic-reference-data pattern as every other status field fixed earlier in this doc. `code` auto-generates as `BOM-000001` etc. (`nextSequentialCode`, same as every other entity). Owner-scoped RLS (open `select`, `owner_id = auth.uid()` on write) — mirrors `asset_requests`/`procurement_items` exactly, verified against their live policies before writing this rather than assumed.
- **`bill_of_materials_lines`** — the flat parts list: `part_name`, `part_number`, `category_id` (reuses the existing `procurement_category` lookup list rather than inventing a parallel one), `quantity` (`> 0`, matches `procurement_items`' own check), `unit_of_measure`, `estimated_unit_cost` (`>= 0` or null — deliberately optional at this stage, refined once real quotes come in), `estimated_total_cost` (generated column, `quantity * estimated_unit_cost`, same pattern as `procurement_items.estimated_total_cost`), and `procurement_item_id` (nullable FK, set once the line is converted — see below). RLS mirrors `bidding_schedule_activities`: open `select`, writes gated by a new `owns_bom(bom_id)` security-definer helper, the same shape as the existing `owns_procurement_item()`.
- Every foreign key on both tables is indexed (`asset_request_id`, `status_id`, `owner_id`, `bom_id`, `category_id`); `procurement_item_id` gets a **partial unique index** (`where procurement_item_id is not null`) so the same Procurement Item can never be claimed by two BOM lines.
- Verified live with `get_advisors` after applying: 0 new `multiple_permissive_policies`, `auth_rls_initplan`, `function_search_path_mutable`, or `rls_disabled_in_public` findings. The only new findings are the same two WARN classes every other table in this schema already carries (`pg_graphql_*_table_exposed` — public schema visibility, expected; and `owns_bom` triggering the same `security_definer_function_executable` class `owns_procurement_item` already does).

**Deliberately left out, flagged rather than built:** no `preferred_vendor_id`/`preferred_contractor_id` on BOM lines — that choice belongs to the generated Procurement Item, not the engineering spec, so it's picked after conversion, not before. No BOM-header cost roll-up display (the per-line `estimated_total_cost` exists in the database; summing it across a BOM's lines in the UI wasn't built). No revision history — if a line's spec changes after it's already been converted, the BOM line and its Procurement Item silently diverge; nothing re-syncs them or warns you. No lock preventing further edits to a BOM once lines are converted or its status is "Approved" — status is currently informational only, not enforced.

### Frontend

- New `bom` entity in `src/lib/crud/configs.ts` (module: Capex Plan, so it shows up in the sidebar next to Asset Requests automatically — the sidebar and routing are fully config-driven, no changes needed there) using the same `lineItems` dynamic-rows editor built for bidding schedule activities.
- Added a second, more general capability to that same line-items engine: `LineItemsConfig["convertTo"]` (`src/lib/crud/types.ts`) — lets a saved line become a row in another entity, via a `mapLine(line, parent, supabase)` function the config supplies. `EntityManager.tsx` renders a **"Generate Procurement Items from Parts List"** button (only when editing an existing BOM) that loops over lines without a linked Procurement Item yet, creates one via the same `createRow()` every other entity uses (so it gets a real sequential `PRC-ITEM-######` code, not a fake one), and links it back via `procurement_item_id`. It's idempotent — already-linked lines are skipped, so clicking it again after adding more parts only processes the new ones, and each converted line gets a small "✓ Converted to a Procurement Item" note. The new Procurement Item's `status_id` can't be hardcoded (lookup_options ids are generated per environment), so `mapLine` resolves "Identified" (the first `procurement_item_status` value by code) at conversion time.
- The line-items modal width now scales with how many columns a given entity's lines have (`fields.length * 170 + 260`, floor 760px) instead of a flat 900px, since a BOM line has twice as many fields as a bidding activity.

### Review — schema

Re-checked against the standing checklist: no missing FK indexes (all six FK columns across both tables are indexed, `procurement_item_id` additionally uniquely so); no circular references (`bill_of_materials → asset_requests`, `bill_of_materials_lines → bill_of_materials/lookup_options/procurement_items`, one direction only — `procurement_items` doesn't reference back); RLS present and per-operation on both new tables, confirmed against `get_advisors` post-apply rather than assumed. The gaps worth your attention are the ones called out above as deliberately not built (no cost roll-up, no revision tracking, no edit-lock after conversion) — none are schema defects, they're scope calls I'd want your read on before building further, since each touches workflow (e.g. should a BOM really become uneditable once "Approved"?) more than data modeling.

## Part 6 — dynamic bidding schedule activities on Procurement Items (no new migration)

Requested: a way to log a procurement item's bidding schedule as a variable list of activities (Pre-bid Conference, Opening of Bids, Post-qualification, Award, ...) — a different set on every item, added and removed freely rather than fixed columns. Turned out the database side of this already existed live: `bidding_schedule_activities` (`activity` text, `planned_date`, `status_id` → a `bidding_activity_status` lookup_options list: Pending/In Progress/Completed/Delayed/Cancelled, `procurement_item_id` FK) was part of the live-only migration history reconstructed back in Part 0, with full owner-scoped RLS (`owns_procurement_item()`) already in place — but no frontend had ever been built against it. This was a frontend-only change.

Added a general-purpose "line items" capability to the CRUD engine, not a one-off for this table, so the same pattern is reusable for any other entity that later needs a dynamic child list:
- `src/lib/crud/types.ts` — new `LineItemsConfig` (child table, parent FK column, its own `fields: FieldDef[]`, and an `emptyLine()` for what a freshly-added row starts as), and an optional `lineItems?: LineItemsConfig` on `EntityConfig`.
- `src/lib/crud/service.ts` — `listLineItems()` fetches a parent's existing child rows; `saveLineItems()` reconciles an edited array against what's in the database (delete rows removed from the list, update rows still present, insert rows with no `id` yet) — called after the parent row itself is saved, so a brand-new parent's id is always known by the time its lines are persisted. `clean()` (drops `""` down to `null` before writing) is now exported so this can reuse it.
- `src/components/crud/EntityManager.tsx` — a new `LineItemsEditor` renders the child rows as a small editable table below the entity's own fields, with an "Add" button that appends a blank row and a "Remove" button per row; `handleSave` validates and persists the lines alongside the parent record on the same Save click. Lines can be added while creating a brand-new Procurement Item too, not just when editing an existing one — they're just held in local state until the item itself is created, then written with the new item's id.
- `src/lib/crud/configs.ts` — wired onto the `items` (Procurement Items) entity: `table: "bidding_schedule_activities"`, fields Activity (text), Planned Date (date), Status (the `bidding_activity_status` lookup).

Follow-up, same part: activities added this way now also show up on `src/app/(app)/schedule/page.tsx` (the Annual Procurement Schedule) — a fifth "Bidding Activity" lane, one row per activity, teal-colored, labeled with the activity name and the parent procurement item's code. Since an activity is a single planned date rather than a start/end range, it renders as a one-month-wide marker on whichever month that date falls in (`start`/`end` both set to `planned_date`). No new migration; just a fourth query added alongside the existing three, following the same `lookup_options!status_id` embed pattern.

Second follow-up: the schedule page was locked to the current year (`new Date().getFullYear()`, no way to see any other year). Made it multi-year: the year is now a `?year=` query param on `/schedule` (defaulting to the current year on anything missing or unparseable), with Prev/Next arrows and a jump-to dropdown (current year ± 5) in the page header. No database change — the existing per-row year filter and month math already worked off a `year` variable, this just makes that variable come from the URL instead of always being "now."

Suppliers and contractors were kept as two tables rather than one table with a type flag because they carry genuinely different fields (contractors: specialty, license number, insurance expiry; suppliers: none of that) — same reasoning the schema-design convention asks for when denormalizing or splitting entities, applied to `not` merging them here.

`contractors` mirrors `vendors`'s shape and RLS pattern exactly: shared reference data, any authenticated user can create/edit, no delete policy. A new `contractor_specialty` lookup_options list backs a `specialty_id` field (Civil Works, Electrical, Mechanical, IT Services, Facilities Maintenance, Logistics, Consulting, Other).

Integrated into procurement at every point suppliers already were, each new column nullable and **mutually exclusive** with its supplier equivalent via a check constraint (a line is sourced from a supplier or a contractor, never both — enforced in the database, not just the UI):
- `procurement_items.preferred_contractor_id` alongside `preferred_vendor_id`
- `purchase_orders.contractor_id` alongside `vendor_id`
- `vendor_biddings.awarded_contractor_id` alongside `awarded_vendor_id`
- `vendor_bids.contractor_id` alongside `vendor_id`

The RFQ award-validation trigger from migration 0014 (which blocks awarding an RFQ to a vendor who never bid on it) is extended to validate contractor awards the same way, against `vendor_bids.contractor_id`.

**Frontend note:** while wiring the new fields into `procurement_items`, `vendor_biddings` (RFQs), and `purchase_orders`, I also fixed those three entities' `category`/`status` fields, which were still hardcoded `type: "select"` enums against column names (`status`, `category`) that migrations 0008–0011 had already replaced with `status_id`/`category_id` foreign keys into `lookup_options` — this is the frontend/lookup_options mismatch flagged as unfixed in Part 0/3 above. I only fixed it on the three entities this task touched, since fixing it everywhere is a bigger, separate job I don't want to fold into this one silently. **The other five entities (Capex Budgets, Asset Requests, Project Charters, Milestones, Risk & Issue Log) are still on the broken old field names** — their status/category/priority dropdowns will fail to save against the live database. The dashboard's KPI tiles (`Active Projects`, `Open Risks`) also still read the old `status` text field and will silently undercount, since nothing there throws — it just never matches.

This needed a small, generic CRUD-engine change to support: two fields on the same entity referencing `lookup_options` but filtered to different `list_key`s (e.g. a procurement item's category and status are both `lookup_options` rows, just different lists). Added `refFilter` to `FieldDef` (`src/lib/crud/types.ts`), an optional filter param on `referenceOptions()` (`src/lib/crud/service.ts`), and re-keyed `EntityManager`'s reference-option cache by field name instead of table name so two differently-filtered fields on the same table don't clobber each other. ## What was wrong (found in Part 0 investigation + original ask)

**1. Vendor identity was free text, not a normalized entity (3NF violation).**
`vendor_bids.vendor_id`/`vendor_name`, `purchase_orders.vendor_id`/`vendor_name`, `vendor_biddings.awarded_vendor_id`, and `procurement_items.preferred_vendor_id` all stored vendor identity as plain text with no backing table. `vendor_name` is functionally dependent on `vendor_id`, not on each row's own primary key — textbook 3NF violation — so the same vendor's name could drift out of sync across rows, "Acme Corp" vs "ACME Corp." wouldn't be recognized as the same vendor, and nothing enforced that `awarded_vendor_id` actually named a vendor who bid on that RFQ.

**2. Every owner-scoped RLS policy on live was one `for all` per table, and several used unwrapped `auth.uid()`.** Confirmed via Supabase's own advisor: 25 `multiple_permissive_policies` warnings and 14 `auth_rls_initplan` warnings (the latter meaning `auth.uid()` was being re-evaluated per row instead of once per query — a real performance cost, not just style). `vendors.created_by` and a couple of helper functions also had a mutable `search_path`, flagged separately.

**3. (Not yet fixed — see "Not changed" below) A newly-discovered, separate issue: the frontend doesn't know about `lookup_options`.** Migrations 0008–0011, applied to live before this session, replaced `status`/`category`/`priority`/`asset_category` text columns with `status_id`/`category_id`/`priority_id`/`asset_category_id` UUID FKs. `src/lib/crud/configs.ts` still defines these as `type: "select"` fields with hardcoded string-literal options against the old column names. This predates this session's work and is unrelated to the vendor fix, but it means most entity create/edit forms with a status/category/priority field are likely broken against the live schema right now — see the flagged section below.

## Assumption flagged (please confirm)

**`vendors` is shared reference data, not owner-scoped.** Every other top-level table in this schema restricts writes to `owner_id = auth.uid()`. Vendor identity is different: it's real-world shared state, and if "Acme Corp" were owner-scoped, every analyst who deals with Acme would have to recreate their own private "Acme Corp" row — which defeats the entire point of normalizing vendor identity in the first place. So any authenticated user can create or edit a vendor record, and there's deliberately **no DELETE policy** — removing a vendor referenced by historical bids/POs should go through a service-role script that reassigns or nulls those references first, not the public API. If you'd rather vendors be owner- or role-restricted, that's a small follow-up migration — say the word.
